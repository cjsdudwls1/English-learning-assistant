## 판독 규칙

이 세트는 **전 페이지에 교사 빨간펜 채점 흔적**이 있다. 그래서 규칙을 명시했다:

- `user_answer` = **학생의 연필 마킹만**
- 교사의 빨간 V/O/밑줄/정정 필기는 **절대 `user_answer`로 쓰지 않는다**

빨간 정정 필기를 학생 답으로 흡수하면 confident-wrong이 나온다 — 이 표본의 핵심 검출 목표다.
(예: 146쪽 Q8은 보기 ⓐ~ⓔ 위에 교사가 `by`/`in`/`on`을 빨간펜으로 적어놨다. 학생 답은 선택지 ②다.)

## 검수 결과 3 — 규약 판단이 필요한 것

### (1) 143·145쪽 섹션별 번호 재시작 — 하네스가 채점하지 못한다

Unit Exercise는 섹션 A/B/C가 **각각 1부터 다시 번호를 매긴다.** 한 페이지에 `1`이 세 개 있다.

`score.mjs`의 매칭 키가 이걸 감당하지 못한다:

```js
// eval/harness/score.mjs:24
export function normalizeProblemNum(v) {
  const s = String(v).trim();
  const m = s.match(/\d+/);   // 첫 숫자열만
  return m ? m[0] : s;
}
```

`"A-1"` · `"B-1"` · `"C-1"`이 전부 `"1"`이 되고, `byNum` Map에서 **마지막 항목만 살아남는다.**

**추정이 아니라 실측이다.** GT를 그대로 되돌려주는 "완벽 예측"을 `scoreRun`에 넣은 결과(147쪽 복원 후 재실행):

```
[빈 출력]   mc 10 abstain, multi 1 abstain, text 33 abstain, multi_gt_invalid 0  — 크래시 없음
[완벽 예측] mc 10/10 correct, multi 1/1 correct, text 19 correct + 14 wrong
```

**완벽한 예측인데 14문항이 wrong으로 찍힌다.** 전부 143·145쪽이고, 예측이 A 섹션 문항인데 GT는 같은 번호의 C 섹션 문항과 대조되는 식이다:

```
05.jpg A-1  gt "on"    vs pred "at night"            → wrong   (C-1과 충돌)
04.jpg A-3  gt "to"    vs pred "is full of fish"     → wrong   (C-3과 충돌)
04.jpg B-1  gt "through,through" vs pred "is good at science" → wrong (C-1과 충돌)
...
```

- **146·147쪽 15문항은 지금 바로 채점 가능** — 완벽 예측에서 `wrong` 0
- **143·145쪽 29문항은 현행 하네스로 정상 채점되지 않는다** (완벽해도 14 wrong)

라벨에는 섹션 접두(`A-1`)를 그대로 살려 뒀다 — 지면의 사실이 그렇기 때문이다. 고치려면 코드 쪽이 바뀌어야 한다:

| 안 | 내용 | 비용 |
|---|---|---|
| (a) 라벨을 1~16 통번호로 바꿈 | 지면과 다른 번호를 GT에 넣게 됨. 모델이 `A-1`을 뭐라 출력하든 맞출 수 없다 | 낮음 / 정확성 손해 |

## 답변 — 사전 고정 스키마를 안 잡는 방식이 가능한가

> "이 모든 문제가 이세상의 모든 문제를 스키마 및 db화 해두려는 것 때문에 생기는 건데, 이를 극복할 방법이 없을까? … ai가 파싱 즉시 스키마 및 db에 추가하거나 html 형태로 보여주거나 해서 미리 스키마를 잡아 두지 않는 방식 같이…"

진단이 정확하다. `multi_select` 추가, `multi_blank` 미구현, `A-1` 번호 충돌 — **세 개가 전부 같은 병의 증상**이다. "문제 형태를 미리 열거해 둔 고정 스키마"에 새 형태가 안 맞아서 매번 코드를 고치는 것.

### 다만 원인은 "스키마화" 자체가 아니라, 한 스키마가 두 일을 겸하는 것

지금 `answer_format` 하나가 두 가지를 동시에 표현하려 한다:

- **(A) 지면 재현** — 이 문제가 종이에서 어떻게 생겼나 (빈칸 3개짜리 표, A/B/C 섹션, 그림 딸린 문항…)
- **(B) 채점 판정** — 맞았나 틀렸나

(A)는 **무한하다.** 교재마다 조판이 다르고 새 유형이 계속 나온다. 여기에 스키마를 씌우려는 한 열거는 끝나지 않는다.
(B)는 **유한하다.** 채점에 실제로 필요한 건 정답값의 대수적 형태 3가지뿐이다:

| 형태 | 뜻 | 지금 이름 |
|---|---|---|
| `one` | 값 하나 | 기본(mc·text) |
| `set` | 순서 무관 집합, 완전일치 | `multi_select` |
| `list` | 순서 있는 리스트, 인덱스별 비교 | `multi_blank` |

**이 3개는 문제 유형이 아니라 값의 모양이라서, 새 문제 유형이 몇 개가 나와도 늘어나지 않는다.** "짝 선택지 (A)/(B)"도 `list`, "3개 고르기"도 `set`, "표 채우기 6칸"도 `list`다.

### 그래서 실질적인 해법은 두 층 분리다

- **원본층 — 스키마 없음.** 모델이 낸 구조를 `JSONB` 한 컬럼에 통째로 보관하고, 화면에는 그걸 렌더링(HTML/마크다운)한다. 새 유형이 와도 마이그레이션 0. 말씀하신 "미리 스키마를 잡아 두지 않는" 부분이 바로 여기다.
- **채점층 — 최소 고정 스키마.** `answer_value JSONB` + `cardinality enum('one','set','list')` 두 컬럼. 채점기는 `answer_format` 문자열이 아니라 `cardinality`로 분기한다.

### "AI가 파싱 즉시 스키마/테이블을 추가"는 권하지 않는다

런타임 DDL이라 테이블이 무한 증식하고, **이 제품의 핵심 가치인 통계가 무너진다** — "이 학생의 전치사 정답률", "반 평균 취약 유형"을 뽑으려면 결국 전 테이블을 join해야 한다. 반대로 전부 HTML 렌더링만 하면 채점·통계가 아예 사라진다.

비용도 짚어두면, 비싼 건 동적 DDL이지 JSONB 보관이 아니다. **JSONB는 지금 스키마에 컬럼 두어 개 추가하는 수준**이라 "비용 효율적으로 불가능"하지 않다.

### 이 프로젝트에 적용한다면

| 대상 | 지금 | 바꾼다면 |
|---|---|---|
| `problems` | 정규화된 컬럼들 | `raw JSONB` 추가 — 모델 원출력 무손실 보관(재파싱·재채점 가능) |
| `labels.answer_format` | 유형이 늘 때마다 열거값 추가 + 채점 코드 분기 추가 | `cardinality` 3값으로 분기. `answer_format`은 **표시 전용**으로 강등 |
| `problem_number` | 스칼라 문자열 → `A-1`·`C-1` 충돌 | `section` + `number` 두 필드, 또는 충돌 없는 `problem_key` 하나 |

번호 충돌도 같은 병이다. "문제 번호는 정수 하나"라는 사전 가정이 지면 현실과 안 맞아서 생겼다.

### 권고

1. **지금**: 위 (1)의 (b)안으로 번호 충돌만 막는다 — 작고 되돌리기 쉽다.
2. **다음 스키마 손볼 때**: `cardinality` 3값 + `raw JSONB`로 정리한다. 이후 새 문제 유형은 **채점 코드 변경 없이** 흡수된다.
3. 렌더링을 HTML로 가는 건 (A)층에만 적용한다. 채점·통계 경로는 구조화된 채로 둔다.

## 병합 시 주의

- `_confidence` / `_note` / `_case` / `_case_type` / `_critical_check` / `_harness_note` / `_placeholder` / `_answer_key_evidence` / `answer_key` 등 **밑줄 접두 필드와 `answer_key`는 검수용**이다. `ground-truth.json`에 넣을 땐 제거해야 한다(하네스가 모르는 키).
- `_placeholder: true` 스칼라는 `multi_blank` 9문항에 있다. text 경로가 스칼라를 참조하므로 유지했다. `multi_select`(147 Q10)에는 없다 — 참값은 배열뿐이다.
- 145 B-3의 스칼라·배열 항목은 `ambiguous` 형태다. `value` 키가 없으므로 `q.user_answer.value`를 무조건 참조하는 코드가 있으면 `undefined`가 된다 — `score.mjs`는 `ambiguous`를 먼저 보므로 문제없다.
- 147쪽에 학생 이름 손글씨("Rami English"는 학원 도장, 그 위 필기는 이름)가 있다. GT 파일 자체엔 이름을 적지 않았다.
- 해설지 2장은 `pages`에 넣지 않았다. 학생 답이 없는 정답 원천이므로 라벨 대상이 아니다.
